# 论文笔记：SoK: Software Compartmentalization

- **作者**：Hugo Lefeuvre（UBC）、Nathan Dautenhahn（Serenitix）、David Chisnall（SCI Semiconductor）、Pierre Olivier（曼彻斯特大学）
- **发表**：IEEE S&P 2025（第 46 届）；arXiv:2410.08434（v1，2024-10-11）
- **本地 PDF**：`papers/SoK_Software_Compartmentalization_SP25.pdf`（arXiv v1，共 20 页）
- **一句话总结**：提出一个统一的"软件隔间化"模型，把问题拆成 P1 策略定义、P2 隔间抽象、P3 隔离机制三层；用这个模型梳理了 211 篇研究和 61 个主流已部署系统，指出学术研究与工业实践之间存在系统性脱节。

---

## 1. 问题与动机

- 隔间化（compartmentalization）是最小权限原则在单个程序内部的落地：把大程序拆成多个低权限组件，一个组件被攻破也不会殃及全局。
- 这一思路从 qmail、Postfix、OpenSSH 开始已有约 20 年历史，学术研究也很多，但**至今仍不是主流工程实践**。例如隔离密钥的提法由来已久，主流密码库却一直没有采纳。
- 论文认为根本原因之一是领域内术语和分析方法不统一，各项工作之间难以比较，研究重点也与实际需求错位。

## 2. 统一模型（§2）

### 2.1 基本概念

| 概念 | 定义 |
|---|---|
| 主体（subject） | 计算单元，如一条指令、一个线程 |
| 客体（object） | 权限施加的单元，如一个内存字节、一个 socket |
| 权限（permission） | 主体能对客体执行的操作，如读、写 |
| 保护域（protection domain） | 权限集合完全相同的最大主体集合。**作者有意从主体角度定义，以贴合当前以代码为中心的主流做法** |
| **定义 I：隔间化** | 对程序 P 的隔间化 =（1）把 P 划分为两个及以上保护域（即隔间）的策略 +（2）该策略的运行时强制执行 |

- **范围**：只讨论单个程序内部（应用、内核、hypervisor、固件都可以）。跨程序的隔离（VM、容器、整应用沙箱、用户态/内核态隔离）不在讨论范围内。
- **接口安全（interface safety）**：验证隔间边界上的所有控制流和数据流。验证不到位会导致**混淆代理（confused deputy）**漏洞。这是隔间化的核心难题，本质上是信息流控制问题在隔间场景下的实例。
- **评价隔间化方案的四个维度**：安全性、性能、兼容性、可用性。没有银弹，各方案只是在这四者之间取不同的折中。

### 2.2 三个关键区分维度

**（1）主体选择：以代码为中心 / 以数据为中心 / 混合** ← 与本课题直接相关

| 类型 | 主体是什么 | 保护域是什么 | 例子 |
|---|---|---|---|
| 以代码为中心（code-centric，又称 spatial，空间维度） | 程序指令 | 代码区域 | 把 libjpeg 单独放进一个域 |
| 以数据为中心（data-centric，又称 temporal / horizontal，时间维度） | 时间维度上的执行单元（线程、进程） | 一个或多个执行单元 | Web 服务器的 worker 进程，各自隔离地运行同一段处理循环 |
| 混合（hybrid，又称 object-oriented） | 被限定在某段代码区域内的执行单元 | — | 线程被绑定在某个库内 |

> ⚠️ **注意**：SoK 里的"以数据为中心"**不是**"围绕敏感数据划分"，而是"按执行实例（线程、进程、请求）划分"。"以代码为中心"也不等于"不关心数据"：以代码为中心的方案同样要决定每个隔间能访问哪些数据（客体）。

- **Insight 1**：
  - 不信任对象能落到某个具体代码单元上时（如第三方代码），或者秘密与特定数据结构绑定时（如密钥），适合以代码为中心。
  - 程序处理多条互不信任的信息流、每条流各有秘密时（如服务多个互不信任客户端的 Web 服务器），适合以数据为中心。

**（2）目标属性**
- 完整性：主体不能写出自己的域。完整性是其他所有属性的前提。
- 机密性：主体不能读出自己的域。
- 可用性：主体不能阻止其他域正常执行。
- 附加属性：
  - **跨隔间控制流完整性（CC-CFI）**：跨隔间调用点只能调用全局 CFG 中合法的入口点。
  - **运行时重新隔间化（runtime re-compartmentalization）**：运行时调整策略，比如随负载变化改变安全与性能的折中。

**（3）信任 / 威胁模型**
- 沙箱（sandbox）：降低不可信主体的权限，保护系统其余部分。例子：Web 服务器的请求解析器。
- 保险箱（safebox / vault）：降低除可信主体外所有部分的权限。例子：保护密钥。
- 相互不信任（mutual distrust）：双方互相剥夺对方的权限。
- 所有方案都依赖一个可信计算基（TCB），通常包括 CPU 和隔间运行时（即参考监视器），有时还包括编译器、内核和库。
- **Insight 2**：不存在统一的"隔间化威胁模型"。

## 3. 分类体系（§3）：P1 / P2 / P3

论文把隔间化拆成三个问题，并指出几乎所有工作都只解决其中一部分：

| | 问题 | 由什么解决 | 代表工作 |
|---|---|---|---|
| **P1** | 应该强制执行什么策略？ | 策略定义方法（PDM） | SOAAP |
| **P2** | 怎样在软件、编程模型里表达策略？ | 隔间抽象（abstraction） | SMVs |
| **P3** | 运行时怎样强制执行？ | 隔离机制（mechanism） | Donky |

文献筛选过程：2003–2023 年安全与系统顶会共 9083 篇，按标题筛到 923 篇，读摘要后保留 96 篇；再滚雪球补 66 篇、按作者经验补 49 篇，共 211 篇。其中 106 篇进入表 1–3。

### 3.1 P1：策略定义方法（PDM）

**定义 II**：PDM 是定义程序权限分离策略的方法，负责识别主体、客体以及要强制执行的权限。

**自动化程度（四级）**

| 级别 | 说明 | 代表 |
|---|---|---|
| 手动 | 开发者在最底层直接指定"哪个主体对哪个客体有什么权限"。可以做到准确，但容易出人为错误：权限给少了影响可靠性，给多了削弱安全性 | 大量工作 |
| 引导式手动 | 仍然手动，但有工具辅助，常带反馈环 | SOAAP、RLBox |
| 策略细化 | 开发者给出高层策略，由工具自动细化为底层策略 | Glamdring、Cali、SeCage、PtrSplit、PrivTrans、KSplit |
| 全自动 | 无需策略输入，基于数据依赖分析做最小权限划分 | ProgramCutter、µSCOPE、SCALPEL |

- 全自动方法的缺点：受软件架构影响，机密数据与不可信部分之间本来就可能存在数据依赖，导致划分结果的安全性变弱。
- **Insight 3**：PDM 防住混淆代理和信息泄露的能力，取决于它对软件语义的理解，而自动化程度越高，这种理解越弱。因此策略细化和全自动方法本质上是**用安全性换开发者的工作量**。

**策略语言**
- **标注（annotations）**：细粒度、局部语义，例如"key 是机密的""parse() 是敏感的"。与代码紧耦合，可能被供应链攻击篡改。
- **放置规则（placement rules）**：粗粒度、全系统层面的信任关系，例如"把库 X 和库 Y 放进不同的域"。与代码解耦，通常由系统集成者编写，可以是 JSON 或构建系统里的配置。
- **Insight 4**：两者表达能力互补，应当结合使用，但目前很少有工作这样做。

**划分粒度**：函数、库、链接单元（CompartOS）、**驱动（KSplit）**、软件包（Enclosure、BreakApp）等。
- 粒度越细，越接近最小权限，也可能找到对性能更有利的边界。但策略越难表达和推理；边界落在封装性差的内部层次上，接口更容易出现混淆代理；还会带来状态爆炸、性能和聚类分析上的难题。

**分析技术**

| 方法 | 用于确定权限时 | 局限 |
|---|---|---|
| 静态分析 | 完备但保守：保证功能正确 | 隔间可能权限过大 |
| 动态分析 | 授予的权限都是确实需要的 | 存在覆盖率问题，可能权限不足、部分负载下功能失效。表 1 的 27 个 PDM 中只有 5 个是动态的 |
| 混合分析 | 两类结果难以组合 | SeCage 把两者的差集当作"可疑集合"，放行但上报；PrivTrans 用动态结果做优化 |

- **Insight 5**：静态分析导致权限过大是公认问题，但从未被量化。

**主体选择与 PDM**
- **Insight 6**：所有自动化 PDM 都是以代码为中心的；非以代码为中心的 PDM 全部属于手动或引导式手动。原因推测有二：以数据为中心的方案本身不那么流行；许多自动化的以代码为中心 PDM 假设程序是单线程的，而以数据为中心的划分需要处理并发，分析更复杂。因此作者呼吁研究面向以数据为中心和混合主体的自动化 PDM。

**通用性**：多数 PDM 针对特定语言。例如 PtrSplit 针对 C 语言的指针别名，RLBox 利用类型系统判断哪里需要做 API 净化。

### 3.2 P2：隔间抽象

**定义 III**：隔间抽象定义并实现在程序中表达分离策略的原语。

**五个核心原语**
- **CREATE / DESTROY**：隔间的生命周期，以及新隔间的默认权限
- **CALL / RETURN**：跨隔间控制流。最低安全要求有三条：
  1. 入口点必须合法，不能调用或返回到其他隔间的任意代码
  2. 切换调用栈，并适当清理寄存器
  3. 与系统其他接口安全组合
- **ASSIGN**：跨隔间授予或撤销权限，即数据共享和资源归属

原语可以是显式的（暴露给开发者），也可以是隐式的（由框架自动处理）。与 PDM 耦合的抽象通常是隐式的。

**CALL 语义**
- 同步：语义上等同于普通函数调用，对程序透明。
- 异步：调用方继续执行，返回结果像消息一样处理。兼容性破坏大，但能掩盖跨域延迟。
- 一旦要支持可用性，就必须处理超时、被调隔间崩溃等新的错误类型，调用语义会带上异步特征。

**ASSIGN 语义**
- 消息传递：系统性地拷贝、编组、检查数据，安全性好，但兼容性和性能代价大。
- 共享内存：通过 load/store 直接通信，兼容性好、性能高，但"在安全上可能有欺骗性"，拷贝不再是默认行为，还容易出现 TOCTOU 问题。
- **Insight 7**：历史上抽象多为异步加消息传递；近年改造遗留软件的趋势转向**同步加共享内存**，这带来了不小的安全和性能代价。

**主体选择对抽象的影响**
- 以代码为中心的抽象：代码与隔间直接对应，CREATE/DESTROY 是隐式的，**隔间是静态的，数量和内容在编译时就已确定**。
- 以数据为中心的抽象：CREATE/DESTROY 是显式的，隔间是动态的，数量和内容取决于运行时控制流。
- 混合抽象：类似以数据为中心的抽象，但可以限制隔间能使用的代码，因此既能实现以代码为中心的划分，也能实现以数据为中心的划分。

**线程模型**
- 正交模型：线程随 CALL/RETURN 跨越保护域，需要正确更新线程状态，并定义好线程局部存储（TLS）的行为。**只适用于以代码为中心的方案。**
- 耦合模型：线程创建时就固定属于某个域，CALL 时在目标域中派生新线程。适用于任何主体选择。

**内核态的特殊性**
- 内核和 hypervisor 的代码通常假设自己对硬件和用户数据拥有"环境权限"（ambient privilege），因此 TCB 的边界和改造方式都不如用户态明显。
- 还要与中断等底层事件集成，所以抽象必须深入到启动、调度、内存管理和中断处理中。相关工作：Nested Kernel、FlexOS、LVD。

**接口加固（compartment-interface hardening）**
- 多数抽象认为接口安全"与己无关"，把责任推给 PDM（假设策略本身是安全的）或下游开发者（假设组件已加固）。
- 抽象其实可以在多个层面做贡献：
  - 限制可跨接口的类型（LXFI、RLBox）
  - 对跨接口指针强制指向范围（Glamdring、LXFI、RLBox 等）
  - 强制或自动对跨接口数据做检查
  - 约束 API 调用顺序
  - 实施 CC-CFI（FlexOS、CubicleOS）
- 这些措施离不开隔间映射信息：不知道哪段内存属于哪个隔间，就无法校验指针和索引。
- **Insight 9**：认为接口安全与隔间抽象正交是一种普遍误解。

**其他属性**
- 放弃机密性可以零拷贝共享只读数据，只有写共享的数据才需要显式共享，但更容易泄露信息、出现 TOCTOU。
- **Insight 8**：很少有抽象支持可用性，而真实系统普遍需要可用性。可用性涉及资源归属（重启一个域时共享资源能否释放）和状态一致性问题。
- 运行时重新隔间化在对抗场景下存在问题：攻击者可以等待或诱导系统进入最弱的配置，因此只适合非对抗场景。

**组合 P1/P2/P3**：许多抽象与特定机制紧耦合，会造成下游程序对机制的依赖。例如 fork() 让页表很难被替换。近年出现了与机制无关的抽象，如 FlexOS、RLBox。
- **Insight 10**：P1、P2、P3 任何一层的设计决策都会影响整个栈，三者最终必须统筹考虑。

**表 2 中与内核相关的抽象（建议后续精读）**：
- Nested Kernel（页表）
- LVDs / KSplit（以代码为中心，内核组件粒度，基于虚拟化 EPT）
- XFI / LXFI（混合主体，内核组件粒度）
- HAKC（以代码为中心，ARM PAC + MTE）
- VirtuOS、LibrettOS（支持可用性）
- CubicleOS、FlexOS（库操作系统，微库粒度）

### 3.3 P3：隔离机制

**定义 IV**：隔离机制在运行时强制执行由 PDM 定义、通过抽象实现的分离。

**两个最小原语**：保护域原语（至少保证完整性）和通信原语（双向传递数据，并强制控制流入口）。再加上 CREATE，就构成一个通用的隔间化机制。

**有条件（conditioned）机制**：自身不足以独立完成隔间化、需要额外措施补齐的机制。
- 例 1：PKU 需要监控修改 key 的指令（WRPKRU），否则无法强制入口点。
- 例 2：内核态的页表保护。
- **Insight 11**：很多用于隔间化的机制本来不是为此设计的，因此是有条件的，这会影响对它们安全性和性能的评估。

**机制对比（表 3 节选）**

| 机制 | 粒度 | 域数量 | 备注 |
|---|---|---|---|
| 页表 / EPT | 页 | ∞ | 主流系统几乎都依赖页表 |
| 页表 supervisor 位 | 页 | 2 | 只能做单向不信任，内核态下是有条件的 |
| Protection Keys（MPK/PKU） | 页 | 8–1024 | 有条件；切换快，但创建、修改需陷入；可被 Meltdown-PK 绕过 |
| 硬件 capability（CHERI） | 字节 | ∞ | 还能保护"寻址"权限，可以从构造上消除一类混淆代理 |
| 有界检查硬件 / 标签架构（MTE 等） | 字节到字 | 视实现而定 | — |
| SFI（含 WebAssembly） | 字节 | ∞ | 基于软件，推广效果最好 |
| 安全语言 | 字节 | 2（safe/unsafe） | — |

- **Insight 12**：机制在权限种类、粒度、域数量上差异很大，进一步说明需要整体看待隔间化。
- **Insight 13**：性能评估过度关注域切换延迟，忽视了接口检查、系统调用防护、共享堆的分配器加固等其他开销。拿有条件机制和无条件机制直接比较切换开销（如 PKU 与 CHERI）是不合理的。
- **Insight 14**：侧信道问题贯穿 P1–P3。Spectre/Meltdown 能破坏页表、PKU、MPX、PAC、TrustZone 的隔离，软件机制（WebAssembly、eBPF）同样受影响。对策仍处于起步阶段。

## 4. 已部署系统的发现（§4）

研究了 61 个主流隔间化程序（其中 56 个来自对 Debian 1520 个高安装量软件包的筛查），主要发现：

1. **隔间化仍不普遍**：在 1520 个应用中不到 56 个，且大多出自安全背景的开发者。
2. **改造遗留代码是可行的**：OpenSSH、V8、Firefox 都是后期改造的，但因策略过严导致功能回退的情况也出现过。
3. **性能很关键**：Windows NT 3.x 曾把图形栈隔离出去，4.0 因为性能问题又改了回来。
4. **隔离有效但仍有漏洞**：OpenSSH、Nginx 等的隔间成功挡住过代码执行漏洞，但接口安全漏洞屡见不鲜。作者判断："如果隔间化普及，接口安全漏洞将成为明天的主要漏洞。"
5. **PDM 几乎全是手动的**：边界靠人工识别、随时间自然演化，所以粒度很粗，几乎都不超过 2–3 个域。只有 Firefox 库沙箱（RLBox）不是纯手动。
6. **抽象多样，高度重视接口**：以消息传递为主，便于检查跨接口数据。
7. **普遍追求可用性**，与学术界的关注点相反。
8. **机制以页表为中心**：只有 V8（SFI）和 RLBox 不依赖页表，根源是对 fork() 语义的依赖。

## 5. 四大开放挑战（§5）

1. **把 P1–P3 割裂开解决，会得到不合适的方案**：策略无法被现有抽象高效表达，抽象无法映射到机制，硬件也不能高效支持常见的划分需求。需要可组合、能映射到现有和未来各种机制的通用抽象，以及能早期评估全栈开销的工具。
2. **创建和维护安全的隔间策略仍然太难**：需要不依赖开发者写策略的方法，比如聚焦第三方依赖、做自动化通用隔间化；需要理解应用和边界语义的 PDM；需要长期维护工具、自动化接口安全检查，以及面向隔间化的 fuzzing。
3. **威胁模型受到的检验不够**：现有工作假设接口已加固、编译器没有引入安全缺口、共享组件（libc、分配器）没有 bug、内核不会成为混淆代理、硬件没有侧信道，这些假设都不成立。
4. **研究偏离主流需求**：主流系统需要可用性、以数据为中心的划分、同步与异步混合的语义、在通用硬件上运行以及适配硬件异构，而研究在这些方面都不足。

## 6. 与本课题（子研究内容一：以代码为中心的划分方法）的关联

### 6.1 定位

- 研究点一（代码边界识别）和研究点二（数据边界识别）属于 **P1（PDM）**：识别主体（模块代码）、客体（数据）和权限。
- 研究点三（代码与数据的跨模块分离）**连接 P1 与 P2，并为 P3 做准备**：把 P1 的结论落实为内存布局上的隔间（CREATE），以及显式的接口标记（CALL/RETURN、ASSIGN），交给运行时防护机制（P3）执行。这正对应 SoK 的挑战 1：P1–P3 不能割裂。

### 6.2 以代码为中心与以数据为中心：在项目中的分工

- **两种视角互补，不互相替代**：SoK Insight 1 指出它们适合不同的程序特征，混合方式可以兼顾两类特征。
- **项目内的分工**：子研究内容一做以代码为中心的划分，主体是内核模块的代码区域；子研究内容二做以数据为中心的划分，主体是执行实例。
- **SoK 对两部分都有支撑**：
  - 子研究内容一：SoK Insight 1 指出，不信任对象能落到具体代码单元（如有漏洞的驱动）上时，适合以代码为中心。
  - 子研究内容二：SoK Insight 6 和挑战 4 指出，以数据为中心的划分在实践中很常用，却缺少自动化方法，是公认的研究空白。
- **术语上要澄清**：子研究内容一中研究点二的"数据边界识别"不是 SoK 里的"以数据为中心"，而是以代码为中心框架下的**客体归属分析**，即确定每个代码隔间能访问哪些数据。本子里应写明这一点，避免评审认为它和子研究内容二重叠。
- **由此带来的约束**：
  - 内核线程会跨模块执行（正交线程模型），所以调用门必须处理栈切换、权限切换和中断上下文。
  - 选择同步加共享内存语义是为了兼容内核，代价是接口安全必须显式处理（Insight 7、Insight 9）。这正是研究点三"标记"工作的意义所在。
