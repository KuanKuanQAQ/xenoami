## 1. 目的：保护什么

### 1.1 场景

EVL（Xenomai 4 的实时核心）和 Linux 跑在同一个内核里。借助 Dovetail 的中断流水线，CPU 有两个执行阶段：

- **oob**：实时阶段。EVL 的实时线程在这里运行，可以随时抢占 Linux；
- **inband**：普通 Linux 阶段。

实时程序通常分成两半：实时部分做控制、采样；非实时部分做日志、网络、界面。两半之间用 EVL 提供的跨域对象（信号量、标志组、observable、xbuf、proxy……）同步和传数据。

### 1.2 威胁

Linux 很大：几千万行代码、成百上千个驱动、复杂的子系统。它可能有 bug，可能被攻破，可能加载了有问题的模块。我们希望：**即使 Linux 出了问题，实时线程照样正确、按时运行。**

### 1.3 保护目标

保护**线程在实时域运行的正确性和实时性**，落实为三样东西：

| 保护对象 | 含义 |
|---|---|
| **可信内存** | 不可信方不能让可信代码越界读写，不能改可信数据 |
| **实时时间** | 不可信方不能让可信代码无界地自旋、循环、等锁 |
| **可信控制流** | 可信代码不调用不可信代码，不解引用不可信方给的指针，不让不可信的值决定分支 |

### 1.4 明确放弃的

| 放弃 | 理由 |
|---|---|
| 不可信一侧内容的正确性 | 对端本来就不可信，它送来的数据只能当输入 |
| 不可信一侧的活性 | 它可以不读、不写、不唤醒、不释放，我们管不了 |
| 唤醒的精确性 | 唤醒可以合并、可以多余，被唤醒者总要重新检查条件 |

放弃这三样之后，问题就从"保护整个系统"缩小成了"保护可信一侧不被拖下水"，这是后面所有简化的来源。

## 2. 最初的想法，以及为什么不够

### 2.1 最初的想法

EVL 直接调用了大量 Linux 函数。最初的计划（doc 01）是：把 LKL（以库的形式运行的 Linux）链接进 EVL，**把 EVL 对 Linux 的调用换成对 LKL 的调用**。LKL 是可信域里的一份 Linux 代码，这样 EVL 就不再依赖宿主 Linux。

### 2.2 能换的：不碰 Linux 对象的函数

第一个提交 `daed79c` 把一批函数换成了 LKL 的：`rb_insert_color`、`rb_erase`、`strcmp`、`find_first_bit`、`int_sqrt`、`ns_to_timespec64` 等。它们只操作调用者传进来的数据（可信的红黑树、可信的位图），换了以后结果完全相同，没有任何困难。

### 2.3 不能换的：作用在 Linux 对象上的函数

**例子：monitor 唤醒 inband 等待者。** 一个普通 Linux 线程 `read()` 一个 EVL 信号量，睡在 Linux 等待队列上。实时线程 `evl_put_sem()` 后，EVL 要叫醒它（原版 `monitor.c:400-411`）：

```c
if (waitqueue_active(&mon->inband_wait_r))
	wake_up(&mon->inband_wait_r);     /* 在 oob 上则经 irq_work 推迟后再调 */
```

`wake_up()` 一路下去：拿等待队列的锁 → 遍历链表（节点在 Linux 线程的栈上）→ 调用节点里的函数指针 → `try_to_wake_up(task)` → 改目标 CPU 的运行队列。它存在的意义，就是**改宿主 Linux 调度器的状态**。

换成 LKL 有三种办法，都不行：

| 办法 | 结果 |
|---|---|
| 调 LKL 的 `wake_up`，作用于 LKL 自己的等待队列 | **正确性**：那个 Linux 线程不在 LKL 里，叫不醒 |
| 调 LKL 的 `wake_up`，传入宿主的等待队列 | **安全性**：代码是可信的，但锁、链表、函数指针、`task_struct`、运行队列全是 Linux 的数据，依赖没有减少。工程上也不成立：LKL 按另一套配置和体系结构编译，结构体布局都不同 |
| 让 Linux 线程改到 LKL 里去睡 | 等于把 Linux 调度器搬进可信域，可信域就不可信了 |

**另一个例子：oob 系统调用经 fd 找对象。** EVL 调 Linux 的 `fdget(fd)` 查 fd 表。换成 LKL：LKL 的 fd 表里没有这个进程的 fd（正确性）；让 LKL 读宿主的 fd 表：Linux 可以把表项换成别的文件（安全性）。

### 2.4 结论

> **安全与否取决于依赖的数据，不取决于执行的是谁的代码。**

能换成 LKL 的，是不碰 Linux 对象的函数；碰 Linux 对象的函数，换成 LKL 要么结果不对、要么照样依赖 Linux 的数据，只能截断。所以问题不是"用谁的代码"，而是"哪些数据必须可信、哪些依赖必须切断"。

### 2.5 为什么想这个问题会绕圈

试图同时回答"这个对象该放在可信域还是不可信域"和"这个对象该不该迁移到 LKL"，会互为前提：

> fd 表放哪？看谁访问它 → 看 EVL 的查找迁不迁到 LKL → 迁了的话，表项是 Linux 的 `open`/`close` 写进去的，那它们也得迁 → Linux 自己的系统调用又要依赖可信域 → ……

解法是**两个问题分开，按顺序回答**：

1. **先定归属**，不考虑代码来源：Z 的正确性依赖它吗？z 也需要它吗？两边都需要就是交集，要截断。
2. **再定实现**，只针对归 Z 的对象：用 LKL 的代码、自己写、还是截断后已经不需要了。

"迁移"不是把一个对象从 Linux 搬走，而是 Z 另有一份同类的对象，Linux 那份原地不动。例如 fd 表：Linux 保留自己的 fd 表，Z 另建一张句柄表（doc 20），句柄表可以用 LKL 里的 xarray 实现。

## 3. 三个维度

讨论中最容易混的是三对概念。它们是**三个互相独立的维度**：

| 维度 | 划分依据 | 回答的问题 |
|---|---|---|
| 可信 / 不可信 | 正确性依赖谁的数据 | 谁能破坏我 |
| EVL / Linux（含 LKL） | 代码出自哪里 | 用谁的代码 |
| 实时 / 非实时（oob / inband） | 在哪个执行阶段运行 | 什么时候跑 |

三者互不等同：

- Linux 的代码可以可信：LKL、拷过来的纯函数；
- EVL 的代码可以跑在不可信一侧：通知中继在 inband 上的处理函数；
- 可信代码也在 inband 上运行：EVL 对象的创建、销毁路径，inband 系统调用里改可信状态的部分。

唯一的约束是：**实时 ⇒ 可信**。实时线程依赖的一切都必须可信，反过来不成立（doc 14）。

还要避免一个预设："Linux = 不可信"。边界不是按代码来源事先画好的，而是由下面的闭包和截断规则推出来的（doc 12–15）。

## 4. Z 与 z

### 4.1 定义

| 符号 | 定义 |
|---|---|
| **Z** | 必须可信的闭包：实时线程执行的代码，加上它依赖的数据，加上写这些数据的代码，加上这些代码依赖的数据……递归下去 |
| **z** | 无法可信的闭包：纯非实时线程能触及的代码，加上它们能写的数据，加上依赖这些数据的代码……递归下去 |
| **Z∩z** | 交集：同一样东西既在"实时必须依赖"的闭包里，又在"非实时能影响"的闭包里。**这就是要截断的地方** |

用闭包定义的好处是：不需要事先判断某个函数"是 EVL 的还是 Linux 的"，只要追"谁写、谁读、谁调用"，交集自然会显出来。

### 4.2 唯一的规则

> **Z 不依赖 z。**

"依赖"要按最宽的意思理解：

| 依赖的种类 | 含义 | 例子（原实现） |
|---|---|---|
| **值** | Z 读 z 写的值，并据此计算、分支 | oob 系统调用每次读 Linux 凭据（Y4）；`irq_work_queue` 的返回值决定是否放引用 |
| **锁** | Z 拿 z 可能持有的锁 | `wake_up` 拿等待队列锁；xbuf 原来两边共用一把环锁 |
| **代码** | Z 执行 z 的代码 | 调 `irq_work_queue`、`copy_from_user` 里的 `might_fault`；`wake_up` 调节点里的函数指针 |
| **内存** | z 写 Z 的内存 | Linux 等待队列头、`struct irq_work` 嵌在可信对象里（Y1、Y2） |
| **时序** | Z 等 z 推进 | 缓冲满了阻塞，直到 z 取走 |
| **资源** | Z 从一个 z 能耗尽的池子里分配 | oob 信号每次从可信堆分配、由 z 释放（Y3） |

反过来是允许的：**z 依赖 Z**（经过门）。Z 可以给 z 提供服务，只要入口受控。

### 4.3 两个方向

规则只有一条，但违反它的情形分两个方向，修法不同：

| 方向 | Z 为什么要碰 z | 修法 | 文档里的颜色 |
|---|---|---|---|
| **入向**（z → Z） | Z 需要 z 的信息 | 变成 Z 自己的数据（私有副本），或者当作输入校验后用 | 黄色 |
| **出向**（Z → z） | Z 需要 z 去做一件事（唤醒、投递信号、释放） | 只记录、不调用：Z 写自己的记录，z 来取 | 紫色 |

出向原来也是"Z 依赖 z"：调用 z 的函数，本身就是执行 z 的代码、拿 z 的锁、读 z 的值。所以紫色其实是黄色的特例，单独列出来只是因为修法统一。

### 4.4 "只写"为什么也不行

通知看起来是 Z 往 z 写东西，信息只往外流。但往 **z 拥有的结构**里写，就得遵守 z 的规矩：

- 先拿 z 的锁（时序依赖）；
- 顺着 z 内存里的指针写，例如 `list_add` 写 `head->next->prev`，写到哪由 z 决定（内存依赖）；
- 看 z 留下的标志决定下一步，例如 `irq_work` 的 `PENDING`（值依赖）。

纯写要同时满足：地址由 Z 决定、不参与 z 的同步协议、写完不读回任何 z 的东西。对 z 拥有的结构，这几乎做不到。所以出向的修法不是"小心地写 z"，而是**只写 Z 自己的内存**，让 z 来取。

### 4.5 两类例外

| 例外 | 含义 | 例子 |
|---|---|---|
| **只影响自身的输入** | z 能改的某个值，只决定当前线程自己的走向，影响不到其他实时线程和可信状态 | `current->ptrace`、`signal_pending(current)`（Y10）；实时线程选择阻塞等 z 送数据（`oob_read` 等 xbuf 的数据），z 不送，只拖住它自己 |
| **信任基** | 截不断、只能信任的底座 | Dovetail 中断流水线（含 `irq_post_inband`）、体系结构代码（`raw_copy_*_user`）、`evl_current()` 经 `thread_info` 取当前线程、页表、时钟设备驱动的 `set_next_event`（Y8、Y9）。单独列清单（doc 23） |

两类例外都要**记录**，不能默默放过：前者要确认确实只影响自己，后者要列进信任基清单。

## 5. 分析步骤

对每个组件都按同样的步骤做（doc 22 §2 首次成形）：

1. **按功能流程列步骤和标记。** 不按现有的函数和结构体，因为现有实现可能把不同的东西揉在一起（一把锁同时保护了两件事）。
2. **列出每个标记谁写、谁读、放在哪。**
3. **代入 Z/z**：每个标记落在 Z、z 还是交集；交集分入向、出向。
4. **对每个交集选一种截断方法**（第 6 节）。
5. **写出不变式**：无论 z 做什么都成立的性质，以及由什么代码保证。
6. **列出行为变化**：截断往往改变语义（合并、丢弃、返回码）。
7. **验证**：测试套件前后对比，加上专门的压力测试。

工具上，doc 15、17 用 clang 导出字段读写和数据流，自动求闭包，作为第 2、3 步的清单来源；最终判断靠人逐处读代码。

## 6. 五种截断方法

| 方法 | 用于 | 做法 |
|---|---|---|
| 私有副本 | 两边都写、Z 又要信它的状态 | Z 保存自己的一份，只信自己这份；需要时发布只读副本给 z |
| 输入化 | z 对 Z 的影响无法去掉 | z 的值只经门传入、校验或截断后用；或者只当"提示"，取任何值都无害 |
| 只记录、不调用 | Z 要 z 做事 | Z 在自己的内存里挂一条记录、发一个合成中断；z 经门取走副本，自己去执行 |
| 归属单侧 | 原本两边共用、实际上只属于一侧 | 拆开，各管各的 |
| 消除 | 不再需要的依赖 | 改流程，让依赖消失 |

### 6.1 私有副本

**xbuf 的 `fill′`（doc 22）。** 原来 xbuf 两端共用一个计数 `fillsz`，两边都加减。现在可信端自持一份 `fill`（"可信方认定的已写未读字节数"），地址计算只用自己的下标和 `bufsz`。z 那边的计数随它怎么写，可信侧不读回。

**`clock_sleep` 的重启日期（Y5）。** 原来被信号打断后，重启日期存在 Linux 的 `current->restart_block.nanosleep.expires` 里，Linux 改了它就能决定实时线程睡到几点。现在存在可信线程自己的 `evl_thread.restart_expires`。

**oob 权限检查（Y4）。** 原来每次 oob 系统调用都 `cap_raised(current_cap(), CAP_SYS_NICE)`，读 Linux 凭据。现在只看"是否已 attach"：attach 时已经做过权限检查并给线程加上了能力，"已 attach"这件事本身就是可信侧自己的记录。

### 6.2 输入化

**xbuf 的门（doc 22）。** z 消费了多少、生产了多少，只能经门报告一个数 n，可信侧先截断（生产时 `n ≤ bufsz − fill`，消费时 `n ≤ fill`）再计入自己的状态。z 撒谎只会造成数据丢失、重复或内容错误，碰不到越界、时间、控制流。

**提示。** `waitqueue_active()` 读 Linux 等待队列头的一个字，决定要不要发通知。读错成"有人等"，多发一次，无害；读错成"没人等"，z 那边漏一次唤醒，只损失 z 的活性。xbuf 的 `ib_waiting` 也是这样用的。

**monitor 的共享状态（Y11）。** `sstate` 在用户可写的共享内存里。EVL 原本就只信内核一侧的 `type`、`protocol`、`event->gate`，不信 `sstate` 里的副本，这是输入化的现成例子。剩下的字段要逐处审计（doc 24 N3）。

### 6.3 只记录、不调用

**通知中继（`kernel/evl/inband_notify.c`）。** 所有 Z → z 的通知都走它：

```
Z：  置位记录的 PENDING（已置位则合并）
     把记录挂进可信的 per-CPU 链表（关硬中断）
     irq_post_inband(合成中断)                      ← 信任基
z：  合成中断的处理函数经门取一条记录，拿到副本
     按类型执行：wake_up / wake_up_all / wake_up_process / complete / 调用 fn
```

- 记录、链表都在可信内存里；z 只拿副本，写不到记录本身；
- 记录的类型、cookie、`fn` 创建时写定，z 只能决定**什么时候**投递、**投不投递**，不能决定唤醒谁、调用谁；
- 记录大小固定，多次通知合并（信号用累加的位）；
- 对象销毁前 `drain`，等中继放手后再释放记录和它指向的 inband 对象。

**monitor 的例子，改前改后：**

```c
/* 原版 monitor.c:400-411 */
if (waitqueue_active(&mon->inband_wait_r)) {
	if (running_inband()) {
		wake_up(&mon->inband_wait_r);
	} else {
		evl_get_element(&mon->element);
		if (!irq_work_queue(&mon->inband_wake_r))
			evl_put_element(&mon->element);
	}
}

/* 改后 monitor.c:38-43 */
smp_mb();
if (waitqueue_active(&mon->ib->wait_r))           /* 提示 */
	evl_inband_notify_post(&mon->notify_r);        /* 只记录 */
```

EVL 核心里原有的 9 类通知（doc 24 P1–P9：线程切 inband、kthread 启动、信号、monitor、observable、stax、`evl_call_inband`、crossing、element 销毁）全部改成了这样，`kernel/evl` 里已经没有 `irq_work`。Linux 要做的事一件没少，只是从"可信代码亲自调用"变成"可信代码留记录，z 自己去调用"。

### 6.4 归属单侧

**monitor、observable 的等待队列（Y2，doc 25）。** Linux 等待队列头原来嵌在可信对象里，Linux 会改它的锁和链表指针。现在单独分配一个 `struct evl_monitor_ib`，归 z；可信对象里只留一个创建时写定的指针。

**xbuf、proxy 的两端（doc 22）。** 每个环拆成可信端、不可信端、共享部分。下标、预留量、锁原来两边共用，实际上每一端只需要自己那一份，拆开后各管各的。

### 6.5 消除

**proxy 的 inband 读写（doc 22）。** 原来 inband 线程也能读写 proxy 的同一个环，两端都变成混合端。这个接口没有必要（inband 线程可以直接读写目标文件），删掉后交集消失。

**`proxy_oob_poll` 的转发。** 原来在 oob 上调用目标文件的 `f_op->oob_poll`，可信代码调用了不可信的函数指针。删掉。

**每次通知的引用计数（doc 24）。** 原来每排一次 irq_work 先拿一个 element 引用，回调里放掉，z 决定何时放。改成"所有 post 都发生在调用者持有引用时，销毁前 drain"，引用操作本身就不需要了。

**按次分配的信号（Y3）。** 原来每发一个 oob 信号 `evl_alloc` 一块可信堆、由 z 释放；z 不投递就能耗尽可信堆，拖垮所有可信组件。改成每个线程一条固定记录，信号用位合并。

## 7. 几个容易出错的判断

| 误区 | 正确的理解 | 出处 |
|---|---|---|
| 把 Linux 调用换成 LKL 调用就安全了 | 安全取决于依赖的数据，不取决于代码出处 | §2 |
| 先决定对象迁不迁，再决定放哪个域 | 先定归属，再定实现 | §2.5 |
| Linux 的代码都不可信，EVL 的代码都可信 | 边界由闭包推出，不由出处预设 | §3 |
| 可信就是实时 | 实时 ⇒ 可信，反之不成立 | §3 |
| 通知只是"写"，没有依赖 | 写 z 的结构就要拿 z 的锁、读 z 的指针 | §4.4 |
| 在 inband 上直接调 Linux 没关系 | 统一成"可信代码只记录"，才能机械检查；inband 上的 post 在中断开着时同步投递，语义不变 | doc 25 §5.2 |
| 用链表排队就不会满 | 队列节点要占内存；放在可信堆里，z 不消费就能耗尽它。缓冲必须有界，满了只能让生产者等或者丢 | proxy、打印线程的讨论 |
| 要保护管道里的元数据（下标、计数） | 对端就是不可信方，篡改元数据的后果 ⊆ 篡改内容的后果；只需保护越界、时间、控制流 | doc 22 §1.3 |
| `wait_queue_head_t` 是个指针 | 它是嵌入的结构体（锁 + 链表头），链表节点在 Linux 线程的栈上 | doc 25 §3.2 |

## 8. 一个完整的例子：monitor 的跨域唤醒

把第 5 节的步骤完整走一遍（详见 doc 25）。

**1. 流程和标记。** 实时线程 post 信号量 → 改计数 → 唤醒 oob 等待者 → 唤醒 inband 等待者。标记有：计数（共享内存）、EVL 等待队列、Linux 等待队列头、irq_work、element 引用。

**2. 谁写谁读。**

| 标记 | 放在哪 | 谁写 | 谁读 |
|---|---|---|---|
| Linux 等待队列头 | 可信对象里 | Linux 的 `add_wait_queue`、poll | 可信侧 `waitqueue_active`、`wake_up` |
| irq_work | 可信对象里 | Linux 的 irq_work 核心 | 可信侧 `irq_work_queue` |
| element 引用 | 可信对象里 | 可信侧 get；Linux 回调里 put | factory |

**3. 交集。**

| 交集 | 方向 | 依赖种类 |
|---|---|---|
| 等待队列头嵌在可信对象里 | 入向 | 内存、锁 |
| `wake_up` / `irq_work_queue` | 出向 | 代码、锁、值 |
| 回调里放引用 | 入向 | 值（z 决定何时改可信状态） |
| `waitqueue_active` | 入向 | 值 |

**4. 截断。** 等待队列头 → 归属单侧；唤醒 → 只记录；引用 → 消除（drain）；`waitqueue_active` → 输入化（提示）。

**5. 不变式。** 可信对象里没有 Linux 会写的成员；可信代码不调用 `wake_up`、`irq_work_queue`；读 z 内存只有一处提示；z 不投递的最坏后果只是 inband 等待者不醒。

**6. 行为变化。** 唤醒可能合并（等待项都是非独占的，`wake_up` 一次唤醒全部，所以没有实际影响）；销毁时等中继放手。

**7. 验证。** `monitor-*`、`sem-*`、`poll-*` 全部通过；与原版对比 74/78 相同。

**还剩什么。** 写文档时发现 inband 等待路径先拿 Linux 锁再拿可信硬锁，同一段代码既改 Z 状态又改 z 链表，是混合代码。建议改成"门 + 标准等待写法"（doc 25 §7.1）。这也说明了方法的价值：按流程逐个标记过一遍，比按函数看更容易发现这类问题。

## 10. 术语

| 术语 | 含义 |
|---|---|
| Z / z | 必须可信的闭包 / 无法可信的闭包（§4.1） |
| 交集 | Z∩z，要截断的地方 |
| 入向 / 出向 | z → Z 的影响 / Z → z 的通知（§4.3）。早期文档里叫黄色 / 紫色 |
| 门 | z 进入 Z 的入口函数，由 Z 实现，参数一律当输入 |
| 输入 | 来自 z 的值，校验或截断后才能用 |
| 提示 | 取任何值都无害的输入，只决定"要不要多做一次" |
| 只记录、不调用 | Z 写自己的记录、发合成中断，z 经门取副本后自己执行 |
| 通知中继 | 实现"只记录"的公共设施，`inband_notify.c` |
| 信任基 | 截不断、只能信任的底座（doc 23） |
| 只影响自身的输入 | z 能改、但只影响当前线程自己的值 |
| oob / inband | Dovetail 的实时 / 普通执行阶段 |
| LKL | Linux Kernel Library，以库形式运行的 Linux |
