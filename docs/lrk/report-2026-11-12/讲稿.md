# 组会讲稿（2026-11-12）

## 第 1 页　把 EVL 对 Linux 的调用换成调用 LKL：两个问题

我们最初的出发点是：可信域不应该调用不可信域的函数。顺着这个想法，最直接的方案是让 LKL 来承接 EVL 对 Linux 的调用，把 EVL 调 Linux 的地方改成调 LKL。在改的过程中，我们发现这个方案有两个问题。

第一个问题是正确性。EVL 调 Linux，往往不是要用某个功能，而是要操作 Linux 里的某个具体对象。举两个例子：
- xbuf 调 `wake_up()`，要唤醒的是睡在 Linux 调度器上的那个 inband 读者；
- proxy 调 `kernel_write(filp)`，要写的是用户进程在 Linux 里打开的文件。

LKL 有自己的调度器和自己的 VFS，没有这些对象。有人会问：把 Linux 的 `filp` 直接交给 LKL 行不行？那样只是把执行的代码换成了 LKL，操作的仍然是 Linux 的 file、inode 和锁，`f_op` 也仍然指向 Linux 的驱动。而且两套内核的结构布局和锁实现都不同，同时修改同一个对象并不安全。所以，这样做只换掉了代码，依赖的数据一点没变，结果反而不再正确。

第二个问题是实时性。不可信方影响实时域，并不只有"被可信代码调用"这一条路，至少还有三条：
- **数据。** 原来的 xbuf 里，oob 端和 inband 端共用同一把硬自旋锁，inband 端持着这把锁直接修改 `fillsz`。只要 inband 一直持锁，oob 端就只能一直自旋。
- **反向调用。** inband 读者直接调用 `evl_raise_flag_nosched()`，进入了 EVL 的调度。
- **实时路径上本来就有 Linux 代码。** 例如中断流水线，以及 tick 里调用的 `set_next_event()`。

这几种影响都不属于"EVL 调 Linux"，所以换成 LKL 也管不到。

右边这张图说明，"EVL/Linux"和"实时/非实时"是两个独立的维度：
- EVL 目录下的 `xbuf_read`、sysfs 的 show 函数，都运行在非实时域，不需要可信；
- Linux 的中断流水线、`set_next_event`、`raw_copy_to_user`，都运行在实时路径上，必须可信。

数据也一样：原 xbuf 环的下标是 EVL 的数据，却由 inband 直接修改；EVL 线程的状态 `oob_state` 则放在 Linux 的 `thread_info` 里。

结论是：一段代码是否需要可信，取决于它在哪个域执行、它依赖的数据被谁写，和它在哪个目录、谁调用谁无关。

## 第 2 页　回到目标：两个闭包 Z、z 及其截断

于是我们回到起点，先问清楚要保护的是什么。答案是：线程在实时域中运行的正确性和实时性。从这个目标出发，可以推出两个闭包。

**闭包 Z：必须可信的部分。**
1. 实时域执行的代码 F1，以及 F1 依赖的数据 D1，都不能被篡改；
2. 所以写 D1 的函数 F2 也要可信；
3. F2 依赖的数据 D2 也要可信；
4. 依此递归。

**闭包 z：无法可信的部分。**
1. 纯非实时线程能触及的函数 f1 都在不可信域；
2. f1 能写的数据 d1 无法可信；
3. 依赖 d1 的函数 f2 也无法可信；
4. 依此递归。

在双核架构下，这两个闭包有大量重叠。如果不截断，Z 会把绝大部分 Linux 都吸收进来。图中间的交集就是冲突集，例如：
- xbuf 环的下标；
- inband 端可以直接操作的 EVL 等待对象；
- proxy 中两个域都会调用的写端 `do_proxy_write`。

截断，就是把交集里的元素逐个消除。目前我们归纳出三种典型方法：

1. **私有副本。** 可信方自己持有一份数据，不再依赖 z 的那一份。例如：
   - 可信端自己保存下标；
   - 用可信句柄表代替 fd 表；
   - LKL 也属于这一类，但只适用于状态私有的函数，比如分配器、数据结构库，不适用于文件、任务这种和 Linux 共享的对象。
2. **输入化。** z 对 Z 的影响只能以输入的形式进入，由可信代码校验之后，再自己修改可信状态。我们之前讨论过的"门"和"共享数据当输入校验"，其实是同一种方法：区别只在于输入是 z 推过来的，还是 Z 自己拉过来的。
3. **只记录、不调用。** 这是反方向的情况：Z 需要 z 做事时，只留下一条记录，由 z 自己来取、自己执行，可信代码不执行 z 的任何代码。通知中继就是这么做的。

其中输入化最为关键：一份数据只要能被当作输入来校验，写它的函数就不必可信，Z 的递归就在这里停下来。

## 第 3 页　原实现：inband 写路径依赖 Linux 对象，却持 oob 锁、改 oob 状态

以 xbuf 的出站环为例，数据由 inband 写入、oob 读出。图分三层：
- 上层是 Linux 对象，红字标出会改写这些对象的函数；
- 中层是 inband 写路径，按时间顺序排开；
- 下层是 oob 对象。

**先看中层依赖了什么。** inband 写者调用 `xbuf_write()`，进入 `do_xbuf_write()`。这条路径依赖四样 Linux 对象：
- `struct file`：`O_NONBLOCK` 是否生效，看的是 `f_flags`，而 `f_flags` 可以被 `fcntl` 改；
- 当前任务：能否被信号打断，看的是 `signal_pending`，而它由 `kill`、`ptrace` 修改；
- 写者睡在 Linux 的 `wait_queue_head` 上，由 `wake_up` 唤醒；
- 拷贝数据要经过用户缓冲区的页表，`mmap`、`munmap`、`userfaultfd` 都能改变它。

这几个函数一看就是不可信的，所以这条路径只能留在不可信域。

**再看它对 oob 做了什么，也就是图中的红色箭头。**
- 第 1 步拿的锁 `obnd.i_event.wchan.lock` 是硬自旋锁，而且同时是 oob 读者等待队列的锁。
- 第 2 步预留空间，修改 `wroff`、`wrpending`、`wrrsvd`。
- 第 4 步修改 `fillsz`。
- 第 5 步直接调用 `evl_flush_wait_locked()`，唤醒 oob 读者。
- 第 6 步调用 `evl_schedule()`。

也就是说，一段不可信代码在拿 oob 的锁、改 oob 的状态、调 oob 的调度器。

**还有一个时间上的问题，看黄色的预留窗口。** 从第 2 步到第 4 步，`wrpending` 大于 0，oob 读者看不到这批数据。窗口中间的第 3 步是拷贝，拷贝可能缺页，缺页由 Linux 处理，而 `userfaultfd` 可以让这一步无限期地挂起。所以即使 inband 已经放了锁，它仍然能决定 oob 读者什么时候拿到数据。

另外两点：
- 两个域用的是同一份 `do_xbuf_*()` 代码，通过 ring 里的函数指针分派；
- 反方向上，oob 读者读完数据后会调用 `irq_work_queue()`，去操作 Linux 的每 CPU 链表，这是 oob 代码在操作 Linux 对象。

另一个环（ibnd，oob 写、inband 读）是对称的：inband 读者持有 `ibnd.lock`，修改 `rdoff` 和 `fillsz`，并直接调用 `evl_raise_flag_nosched()`。proxy 也一样：转发者调用 `kernel_read/kernel_write`，依赖目标文件，同时修改 `fillsz` 和 `on_error`，并直接调用 `evl_raise_flag()`。

## 第 4 页　改后：可信端自持状态，不可信端只报告结果

改后，inband 写路径只剩四步：
1. 在它自己的等待队列上睡眠；
2. 读取它自己保存的写位置；
3. 把数据拷进共享缓冲区；
4. 调用门 `xbuf_gate_commit(h, n)`，报告"我写了 n 字节"。

全程不持有任何 oob 锁。拷贝时缺页，拖慢的只是它自己。

门里执行的是可信代码，依次是：
1. 加可信锁；
2. 把 `n` 截断到空闲空间以内；
3. 更新可信端自己保存的 `wroff` 和 `fill`；
4. 如果有读者在等，就唤醒它；
5. 放锁。

这段代码有三个特点：工作量有界，不碰用户内存，不调用不可信代码。所以锁一定会被释放；只要可信内存将来做了隔离，锁也不会被篡改。

不可信端仍然能做三件事，但都无害：
- **报告假的 `n`**：截断以后只会影响内容；
- **不停地调用门**：只有在可信端自己的条件发生变化时才会唤醒读者，而且门里的工作量有界；
- **从不调用门**：oob 读者的等待带超时，超时就告警。

反方向的通知改为"只记录"：读者读走数据后，调用 `evl_inband_notify_post()`，只在可信的每 CPU 链表上挂一条记录，然后发一个合成中断；inband 把记录取走以后，自己去调用 `wake_up`。

## 第 5 页　保护可信端，而不是保护管道

我们一共尝试了三个方案。

**方案一：保护管道。** 下标归可信域，不可信方先通过门预留空间，写完再提交。核心问题是：可信端必须记录"对方预留了多少、还没提交多少"，要等不可信方提交完才能发布数据。也就是说，保护管道反而在两端之间制造了耦合，让实时端受不可信方拖累。

**方案二：按端拆分。** 每一端管理自己的下标，两端只共享一个原子计数 `fillsz`。漏洞在于：不可信方不需要写出越界的值，只要把 `fillsz` 写成 `bufsz`，可信写者就永远看到"满"；写成 0，可信读者就永远看到"空"。

**方案三：可信端自持。** 也就是上一页的做法。

那么，为什么不需要保护管道本身？
- 对端就是不可信方，管道里的内容本来就只能当作输入。
- 篡改元数据能造成的后果，无非是丢数据、重复、旧数据、乱序、看到空或看到满；这些后果，对方直接篡改内容也都能造成。
- 只有三类后果是篡改内容做不到、篡改元数据才能做到的：越界、时间、控制流。只有这三类需要截断。

这个结论有一个前提：管道的另一端就是不可信方本身。如果两端都可信、只是途经不可信的内存，就需要另外做完整性保护。
