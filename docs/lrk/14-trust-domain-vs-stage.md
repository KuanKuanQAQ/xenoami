# 14 可信域与 stage：对象归属、读写规则和调用规则

本文整理 2026-11-05 至 11-06 的两轮讨论：

1. 一个对象应该放在可信域还是不可信域？读写它的函数归哪个域？
2. 可信域、不可信域和 oob、inband 是什么关系？

第二轮推翻了第一轮的几处结论，本文只保留修正后的版本，被推翻的地方在 §11 单独列出。doc 12、doc 13 里因此需要修正的地方列在 §12，并在原文对应位置插入了"→ 见 doc 14 §12"的标记。

---

## 0. 结论

> **stage 决定一次执行能得到什么保证；域决定一段内存（代码和数据）的完整性是否受保护。**
>
> 可信域 = oob 执行所依赖的全部代码和数据，也就是 oob 的可信计算基（TCB）。所以**在 oob 上执行的一定是可信代码，反过来不成立**：为 oob 准备状态的那部分 inband 代码也是可信代码，它只需要"不写错"，不需要"按时完成"。
>
> 对象的归属由"oob 是否依赖它的值"决定；函数的归属由"它是否不经门就写了可信对象"决定。

之前的文档（12、13，以及 impl-shared-state/04）默认"可信 = oob、不可信 = inband"，把"只在 inband 运行的 EVL 函数"一律视作 Linux 函数。这对时效性是对的，对完整性是错的。

---

## 1. 基础假设

| 执行 | 保证 |
|---|---|
| 非实时任务，只在 inband 上运行 | 不保证 |
| 实时任务在 oob 上运行 | **保证正确，包括时效性** |
| 实时任务切换到 inband 以后 | 不保证 |

其余都由这三条推出来。

---

## 2. 两个维度

| 维度 | 性质 | 取值 | 回答的问题 |
|---|---|---|---|
| **stage** | 运行时状态，属于一次执行 | oob / inband | 这次执行保证什么 |
| **域** | 内存属性，属于代码和数据 | 可信 / 不可信（另加共享数据区，§5.1） | 这段内存被不被保护 |

同一段代码可以在两个 stage 上执行；同一个任务可以在两个 stage 之间切换。而一段内存属于哪个域，是静态的。

---

## 3. 推导

**第 1 步：oob ⇒ 可信。** oob 执行要正确，它执行的代码、读来做判断的数据就不能被"不保证正确"的一方改掉。所以会在 oob 上运行的代码、oob 依赖的数据，都必须在可信域。等价地说：**不可信代码永远不能在 oob 上运行**。

**第 2 步：可信 ⇏ oob。** oob 依赖的数据，不全是 oob 自己写的：

| inband 上的代码 | 写了什么 | oob 之后怎么用 |
|---|---|---|
| `proxy_factory_build` | `bufsz`、`granularity`、`lock`、`oob_wait` 的初始值 | oob 读写路径全靠它们 |
| `proxy_release` | 踢醒 `oob_wait`，释放 element 引用 | oob 等待者被唤醒，element 生命周期 |
| `evl_switch_oob` 的前半段 | 线程状态 | oob 调度器 |

这些代码只在 inband 上运行，但写错了 oob 就会错，所以它们**必须是可信代码**。

**第 3 步："inband 上不保证"具体不保证什么。** 不保证按时完成，甚至不保证完成：可能被延迟、被 oob 抢占、所在任务被杀。但如果执行的是可信代码，它**写可信状态时不能写错**，否则第 1 步就被破坏了。

---

## 4. 四种组合

| | **oob** | **inband** |
|---|---|---|
| **可信代码** | EVL 的 oob 路径（如 `proxy_oob_*`）；Dovetail 流水线；在 oob 上被调用的 Linux 函数（doc 12 §4.4 的"对 oob 安全的函数"）。**要求：正确，而且时间有上限** | 生命周期代码（工厂 build/dispose、`.open`、`.release`）；门；`evl_switch_oob` 前半段。**要求：见 §4.1** |
| **不可信代码** | **不允许出现** | Linux；非实时任务；转发者 `relay_output` / `relay_input`；实时任务切到 inband 以后执行的 Linux 代码。**没有要求** |

两点推论：

1. **"对 oob 安全的 Linux 函数"是住在 Linux 内存里的可信代码。** 这正是要把它们换成 LKL 或 EVL 自己的实现的原因：只有这样，可信域才能和 Linux 内存分开。03 的 relay 链表就是一个例子：原来 oob 要调用 Linux 的 `irq_work_queue`，现在换成 EVL 自己的实现。
2. **任务在 stage 间切换，它的可信数据不跟着变。** 实时任务切到 inband 后执行的是不可信代码，但它的 `evl_thread` 仍是可信数据，因为 oob 调度器要读。inband 代码只能经门改它，`evl_switch_oob` 就是这样一个门。

### 4.1 跑在 inband 上的可信代码要满足什么

1. **完整性**：写 oob 也会读的状态时，每一步都要保持一致。oob 可以在任意一条指令处抢占它（doc 13 §6 的根本原则），所以要用 hard lock 或原子操作。`ring->lock` 是 `hard_spinlock_t` 就是这个原因。
2. **不卡住 oob**：持有 oob 也会争用的锁时，临界区要有上限，而且不能睡眠、不能调用不可信代码、不能等待不可信代码。
3. **允许半途而废**：它可能被无限期推迟，也可能永远完不成。设计上要保证它停在任何位置，oob 仍然正确。

除此之外，它**可以**做 oob 不能做的事：睡眠、拿 Linux 锁、调用 Linux 函数，前提是这时没有持有 oob 会争用的锁。例如 dispose 里调 `destroy_workqueue`，build 里调 `kzalloc`。

## 5. 对象

### 5.1 三类对象，以字段为单位

| 类别 | 定义 | 例子 |
|---|---|---|
| **可信** | **oob 的执行（直接，或者通过可信代码）依赖它的值** | `fillsz`、`oob_wait`、EVL 一侧的下标、`ring->lock`、`bufsz`、`reqsz`、`evl_thread` |
| **不可信** | oob 不依赖它的值 | Linux 的 `struct file`、`worker_lock`、转发者的下标、`inband_wait`、Linux 的 `raised_list` |
| **共享数据区** | 两边都写，但可信代码只把它当作不解释的数据搬运 | `bufmem` 的内容 |

- **单位是字段，不是结构体。** 同一个结构体里的字段可以分属不同的域，这就是拆结构体的依据（05 把 `proxy_ring` 拆出了 `proxy_relay`）。
- **和"在哪个 stage 被访问"无关。** `bufsz` 只在 inband 上写一次，但 oob 依赖它，所以是可信的。`worker_lock` 是 EVL 分配的，但 oob 不依赖它，所以是不可信的。
- **共享数据区里的内容不受保护。** 不可信一侧可以写错、写完再改（TOCTOU），可信代码只负责搬运，不解释它。所以内容错了只影响使用这份数据的应用，伤不到 EVL。proxy 读方向的数据本来就来自 Linux 文件，它的可信度不会高于 Linux 本身（2026-11-05 的讨论）。

### 5.2 "读"包括间接的读

- **跟着指针走也算读**：读 `filp->private_data` 就是读了 `struct file` 这个 Linux 对象。
- **调用一个会读某对象的函数，也算读了这个对象。**

## 6. 读写规则

| | **可信代码** | **不可信代码** |
|---|---|---|
| **读可信对象** | 随意 | **只能经门**，或者通过只读视图 |
| **写可信对象** | 随意（在 inband 上要满足 §4.1） | **禁止**，只能经门 |
| **读不可信对象** | **受限**：只当数据搬运；或者拷进来、只读一次、校验以后再用 | 随意 |
| **写不可信对象** | **有条件**，见 §6.4 | 随意 |

### 6.1 不可信代码读可信对象：只能经门

从完整性上看这是无害的：读到什么都改不了可信状态，而机密性不在威胁模型里。但仍然要经门，原因有两个：

- **一致性**：多字段的可信对象受可信锁保护。不拿锁会读到撕裂的值；拿锁的话，这把锁就得对不可信代码开放。
- **隔离以后看不见**：可信内存对不可信一侧不映射，或者只读映射。

例子：`relay_output` 要读 `fillsz`，调门 `proxy_gate_out_fill`。

### 6.2 不可信代码写可信对象：禁止

唯一的通道是门，门要做校验。例子：`relay_output` 消费数据要调 `proxy_gate_out_consume`，门里检查 `n <= fillsz`。

### 6.3 可信代码读不可信对象：区分"数据"和"控制信息"

| 读来的东西怎么用 | 是否允许 |
|---|---|
| 当作不解释的数据原样搬运（proxy 把 `bufmem` 拷给用户） | 允许 |
| 当作控制信息：指针、下标、长度、函数指针、标志位 | **不能直接用**。必须先拷进可信内存，只读一次，再校验，否则会有 double-fetch / TOCTOU 问题 |

这条和 stage 无关：不论可信代码跑在 oob 还是 inband，用了不可信的控制信息，可信状态就可能被带坏。门本身就是这种情况的标准形式：门读不可信一侧传进来的参数，校验以后再用。

### 6.4 可信代码写不可信对象：三个前提

1. **地址必须来自可信域。** 如果沿着存在不可信内存里的指针去写，等于让不可信一侧决定可信代码往哪写（write-what-where）。
2. **对锁和等待的要求按 stage 区分**：
   - 在 oob 上：不能要求拿 Linux 的锁，也不能等待。只能用单字写、无锁结构，或者 Linux 能容忍并发写的方式，也就是 doc 13 §8.3 的那几种协议；
   - 在 inband 上：可以拿 Linux 的锁，但这时不能持有 oob 会争用的锁（§4.1）。
3. **不能破坏 Linux 依赖的不变式。** 这条保护的是 Linux 本身，不是可信域。但同样要遵守，比如往 Linux 的链表里插节点，必须遵守它的同步协议。

## 7. 调用规则和等待规则

### 7.1 调用

| 调用 | 调用者在 oob 上 | 调用者在 inband 上 |
|---|---|---|
| 可信 → 可信 | 随意 | 随意 |
| 可信 → LKL | 允许（LKL 是可信域里的一份 Linux 服务；在 oob 上只能调用 LKL 里的无状态函数，doc 13 §9） | 允许 |
| 可信 → 不可信，**同步调用** | **禁止**：等于不可信代码跑在 oob 上 | **允许**，三个条件：调用期间不持有 oob 会争用的锁；返回值当作不可信输入（§6.3）；隔离以后，调用时要切换到不可信的内存权限 |
| 可信 → 不可信，**异步请求**（投递请求，由不可信一侧在自己的上下文里执行） | 允许，例如 `evl_call_inband_from` | 允许 |
| 不可信 → 可信 | 不会发生（不可信代码不在 oob 上运行） | **只能经门** |
| 不可信 → 不可信 | 不会发生 | 随意 |

### 7.2 等待

| 等待 | oob 上 | inband 上 |
|---|---|---|
| 可信核心要往下走，必须等不可信一侧（锁、完成量、引用计数归零） | **禁止** | 允许，前提是不持有 oob 会争用的锁 |
| 应用主动请求一项由 Linux 提供的服务并等结果（proxy 的阻塞读写） | 允许，前提是可以被打断，或者设了超时、非阻塞，而且只影响这个调用者自己 | 允许 |

### 7.3 门要满足的条件

门是可信代码，由不可信代码在 inband 上调用。数量越少越好，每个门还要满足：

1. **校验参数**，参数只读一次；
2. **不睡眠，时间有上限**：门可能要拿 oob 也会争用的锁；
3. **不把可信对象的指针交出去**：不可信一侧只拿不透明句柄；
4. **不在持有 oob 会争用的锁时回调不可信代码**。

## 8. 函数的归属

### 8.1 规则

| 函数在哪个 stage 上运行 | 归属 |
|---|---|
| 会在 oob 上运行 | **必须是可信代码**。它调用的不可信函数必须换掉：换成 LKL、换成 EVL 自己的实现，或者改成异步请求 |
| 只在 inband 上运行，**不经门就写了可信对象** | **可信代码**，要满足 §4.1 |
| 只在 inband 上运行，**只经门碰可信对象** | **可以是不可信代码**。为了让 TCB 尽量小，应该划为不可信 |

所以"这个函数调用了哪一侧的函数"，对 oob 函数是硬约束；对 inband 函数，起决定作用的是"它写不写可信对象"，调用关系只影响拆分成本。

### 8.2 一个函数两边的事都做，怎么办

一个 inband 函数既做 Linux 的事，又写可信对象，有两种处理：

| 做法 | 适用 | 例子 |
|---|---|---|
| **拆函数**：Linux 那部分留在不可信一侧，写可信对象的几处换成门 | 函数主要在做 Linux 的事，碰可信对象的只有几处 | `relay_output`：主体是 `kernel_write`，可信操作只有"读发布量、消费、通知"三处 → 三个门 |
| **整个留在可信域** | 函数主要在写可信对象，Linux 调用只是附带的 | `proxy_release`：全是 EVL 操作；工厂 build：调 `kzalloc`、`alloc_workqueue`，但主要是初始化可信状态 |

判断标准是 TCB 大小和门的数量：拆出去能让 TCB 明显变小、而门又不多，就拆。

## 9. 对象的归属：判定算法

函数的归属依赖对象，对象的归属又依赖函数，所以从两头已经确定的点出发，往中间推。

**第 1 步：固定两端。**

- **固定为不可信**：Linux 原有代码独立访问的对象，例如 `f_flags`、`f_op`、`raised_list`、`struct file`。不改 Linux 就挪不动。
- **固定为可信**：EVL 核心对象，例如调度器、线程、EVL 等待对象和锁、`evl_file`；以及所有在 oob 上运行的代码。

**第 2 步：剩下的对象，看 oob 是否依赖它的值（§5.1），再看访问者在哪个域。**

| 访问者组合 | 对象放哪 |
|---|---|
| oob 依赖它，只有可信代码写 | 可信。不可信代码要读，经门 |
| oob 不依赖它，只有不可信代码访问 | 不可信，例如 `worker_lock`、转发者的下标 |
| oob 依赖它，但不可信代码要写 | 冲突，见第 3 步 |
| 两边都写，可信代码只当数据用 | 共享数据区，例如 `bufmem` |

**第 3 步：解决冲突。**

| 手段 | 适用条件 | 例子 |
|---|---|---|
| **拆对象**：一个结构体拆成可信、不可信两半 | 不同字段的访问者不同 | 05：`proxy_ring` 拆出 `proxy_relay` |
| **拆函数**：不可信部分挪出去，碰可信对象的地方换成门 | §8.2 | 05：`relay_output` |
| **搬对象** | 只有 EVL 自己的函数访问它，Linux 不会独立访问 | 05：`worker_lock` 从 EVL 对象搬到 bridge |
| **副本：快照** | 对象创建后不变 | `bufsz`、`granularity` |
| **副本：镜像加推送** | Linux 写得少，并且能接受加一个推送点（要改 Linux） | 02：`nonblock` |
| **副本：自建一份** | 可信域只是借用 Linux 的服务 | 03：relay 链表 |
| **不访问** | 这次访问在语义上本来就不需要 | 01：删掉对目标文件 `oob_poll` 的转发 |

## 10. 用 proxy 检验

### 10.1 函数落在哪一格

| 函数 | stage | 写可信对象的方式 | 归属 |
|---|---|---|---|
| `proxy_oob_write` / `proxy_oob_read` / `proxy_oob_poll` | oob（`oob_write` 也可能在 inband，见 05 §3） | 直接写 | 可信 |
| `proxy_gate_*` | 两个 stage 都有 | 直接写 | 可信（门） |
| `proxy_release`、工厂 build/dispose、`init_ring`、`destroy_ring` | inband | 直接写 | 可信，inband |
| `relay_output_work` / `relay_input_work` | inband（kworker） | 不写，只转交给 bridge | **不可信**（doc 15 §6 的自动分析结果；原来写成"可信，inband"是错的），可以挪进 `proxy_bridge.c` |
| `relay_output` / `relay_input` | inband | 只经门 | 不可信 |
| `proxy_bridge_write` / `read` / `poll` / `mmap` | inband | 只经门 | 不可信 |

05 的实现和这张表一致。

### 10.2 三处可疑的地方

| # | 位置 | 结论 |
|---|---|---|
| 1 | `relay_output_work` 在 kworker 上同步调用 `proxy_bridge_relay_output` | **不违规**：可信代码在 inband 上同步调用不可信代码，调用时不持锁（§7.1） |
| 2 | `proxy_oob_write` 的 `running_inband()` 分支同步调用转发者 | **不违规**：这个分支只会在 inband 上走到（非 EVL 线程），调用前门已经放了 `ring->lock` |
| 3 | 所有入口第一行的 `element_of(filp)`：oob 入口、`proxy_release`、`proxy_gate_bridge` 等 | **违规**：可信代码直接使用了不可信对象（`struct file`）里的控制信息（`private_data` 指针），没有校验（§6.3）。这和 stage 无关，所有 EVL 设备都有这个问题。oob 入口可以改为从 EVL 自己的 `evl_file` 拿 element；VFS 调进来的入口要在门里校验句柄。**未处理** |

### 10.3 顺带发现的疑点 P7（只读了代码，未验证）

`oob_wait` 是每个 element 一个，不是每个打开实例一个。proxy 是公开 element，可以被打开多次。其中一个 fd 关闭时，`proxy_release` 会把**所有** fd 上的 oob 等待者都踢醒，另一个 fd 上的线程会收到 `-EBADF`，尽管它的 fd 仍然有效。这是原代码的行为。

## 11. 第一轮里被推翻的结论

| 第一轮的说法 | 修正 | 原因 |
|---|---|---|
| 可信代码同步调用不可信代码一律禁止，理由是"不可信代码会跑在可信上下文里，可能睡眠、阻塞" | 只在 oob 上禁止；inband 上满足三个条件就允许（§7.1） | 这个理由是 stage 推理：睡眠、阻塞只对 oob 有害 |
| "可信域不能等不可信域" | 只限 oob 上的执行（§7.2） | 同上 |
| `relay_output_work`、`proxy_oob_write` 的 inband 分支是违规 | 不违规（§10.2） | 同上 |
| "同步调用 Linux 函数的函数，先暂定为不可信" | 只对 oob 函数成立；inband 函数看它写不写可信对象（§8.1） | 可信代码在 inband 上可以调用 Linux |
| "不可信函数读可信对象，函数必须在可信域"（讨论中最初的说法） | 不可信函数可以读，但要经门（§6.1） | 完整性上无害，问题只在一致性和隔离 |
| "可信函数写不可信对象，随意"（讨论中最初的说法） | 有三个前提（§6.4） | 写的地址、锁、Linux 的不变式 |
